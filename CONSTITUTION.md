# CONSTITUTION.md

Non-negotiable standards for the **Tapestry** Zola theme. These constraints hold regardless of which templates, styles, or design tokens change beneath them. Read alongside @CLAUDE.md, not instead of it — this file states *what must always be true*; CLAUDE.md states *how to work day to day*.

Amend this file deliberately and explicitly (see §10). Do not let it erode silently through unrelated operational work.

## 1. Accessibility

- The theme MUST conform to **WCAG 2.1 (or later) Level AA** across all shipped templates and default styles.
- This includes: sufficient colour contrast in both light and dark mode, fully keyboard-navigable interactive elements (including the theme switcher), semantic HTML landmarks and correct heading order, visible focus states, and alt-text support for images inserted via content or shortcodes.
- Verify with automated tooling (e.g. axe via the Playwright MCP server) plus a manual keyboard-only pass before treating any visual or structural change as complete.

## 2. JavaScript

- The theme MUST ship with **no JavaScript**, with exactly **three** exceptions: a **theme switcher**, equivalent in scope to terminus's own `js/theme-switcher.js` at the pinned snapshot (see §3); **client-side KaTeX math rendering**, equivalent in scope to terminus's own `js/katex.min.js`, gated by `extra.katex` with the same page/section/config precedence terminus uses; and a **presentation style/variant switcher**, gated by `extra.presentation_style_switcher` (default `false`, no terminus equivalent — this is a Tapestry-original feature) — and *only* those three scripts, not terminus's JS footprint as a whole.
- Functionally, Tapestry's theme switcher is narrower than terminus's own: it toggles **light ⇄ dark only**. It does not reproduce terminus's `color_scheme` roster of thirteen independently named colour schemes (terminus, tokyo-night, nord, gruvbox-dark, the Catppuccin variants, etc. — see `specs/terminus-compat-contract.md` §9 for the full deviation note). Colour *identity* — which hues a light or dark mode actually uses — is owned entirely by the selected presentation style group and variant (§7, §8), never by the switcher itself.
- KaTeX rendering is otherwise adopted as-is from terminus, with one deliberate deviation: the same `js/katex.min.js` file, the same `extra.katex` config key and precedence, the same webfonts — but `css/katex-swap.css` (KaTeX's own officially published `font-display: swap` variant) is used in place of terminus's `css/katex.min.css` (which uses `font-display: block`). The swap variant is sourced from the same KaTeX release, not patched by hand, so it remains updateable as a clean upstream artefact. This deviation satisfies §4's `font-display: swap` requirement for all `@font-face` declarations without requiring any manual edits to a third-party file. No build-time pre-rendering, no content-authoring workaround — this is a deliberate, explicit exception not a gap to be closed later.
- The presentation style/variant switcher lets a site visitor override the site's configured `extra.presentation_style`/`extra.presentation_variant` at runtime, from a two-level disclosure menu — one entry per style group, each independently expandable (a native HTML exclusive accordion: multiple `<details name="...">` sharing one `name`, so opening one group closes any other open group, with no JS required for that mechanic) to reveal that group's variants — without a page reload. This grouped/accordion structure is mandatory at any group/variant count; a flat listing of every `<style>/<variant>` combination does not scale past a handful of variants and may not be substituted, however few groups or variants a given build happens to implement. The menu opens with the visitor's current style group already expanded, and marks both that group's header and its active variant as current. The full interaction spec — markup shape, accordion mechanics, auto-expand/marking rules, keyboard behaviour — is frozen in `specs/presentation-style-switcher.md`. It is opt-in per site (`extra.presentation_style_switcher = true`; the shipped default is `false`) — unlike the theme switcher, which is unconditionally always present.
- The theme switcher and the presentation style/variant switcher must both degrade gracefully: with JS disabled, the site must still render correctly and remain fully usable — the theme switcher defaults to the system `prefers-colour-scheme`, and the presentation style/variant switcher control simply does not appear (or is inert), leaving the site on its build-time-configured `extra.presentation_style`/`extra.presentation_variant`. KaTeX math is not held to this same no-JS-fallback bar — with JS disabled, KaTeX-enabled pages will show raw, unrendered `$...$`/`$$...$$` source text rather than typeset math (identical to terminus's own no-JS behaviour), which is an accepted degradation, not a defect.
- No analytics scripts, no third-party embeds that require JS, no JS-dependent interactivity anywhere else in the theme. Any request that implies adding JS outside these three sanctioned scripts is a constitutional conflict — flag it, don't implement it.
- At the pinned terminus snapshot, terminus ships two further JS features beyond the theme switcher and KaTeX: a responsive-nav popover auto-closer and a copy-to-clipboard button on code blocks (see `specs/terminus-compat-contract.md` §7 for the full inventory and resolution). Neither is covered by any exception above. Each must be reimplemented without JS or dropped — never carried forward as JS on the assumption that "terminus does it too."

## 3. Terminus compatibility

**Problem:** "Must stay compatible with terminus" is ambiguous if terminus itself keeps changing upstream — compatibility with a moving target isn't a stable, testable requirement.

**Resolution:**

- Compatibility is pinned to a **specific snapshot of terminus**, not to "terminus" as an ongoing project.
  - Pinned reference: terminus @ `aa8d8b67f9ab69ae48e1405f96e152d41f03e0ed`.
- The Zola version itself is pinned for reproducible builds: **Zola `0.23.6`**. Run `zola --version` and confirm it matches before relying on any Zola/Tera feature (per CLAUDE.md's build-command checklist) — a mismatch is a signal to stop and reconcile, not to proceed anyway. `0.23.6` satisfies terminus's own `min_version = "0.22.0"` (`theme.toml`) and the Zola `0.21.0`+ requirement for GitHub-style alerts (`specs/terminus-compat-contract.md` §2, `markdown.github_alerts`). `0.23.x` bundles **Tera v2**, a from-scratch, non-backward-compatible rewrite of the template engine with no macros or shortcodes: reusable template logic is a component that receives `page`, `section`, `config`, `lang` and `taxonomy` explicitly, since components have no implicit access to ambient context.
- That snapshot's shortcodes, config keys, template blocks, and front-matter fields are extracted once into a standalone compatibility contract, checked into this repo at `specs/terminus-compat-contract.md`. **That contract — not the live terminus repo — is the source of truth Tapestry is tested against.**
- The contract is a frozen fixture. It changes only when a deliberate decision is made to adopt a newer terminus feature or drop an old one — never automatically, and never merely because upstream terminus changed.
- "Sync with the latest terminus" is always a separate, explicit task: re-diff the new terminus snapshot against the contract, decide what to adopt, and update the contract intentionally.
- This repo's actual live usage (`content/` and `config.toml` as they exist today) is the hard floor: whatever shortcodes/config keys are currently in use are non-negotiable regardless of what the contract says. The contract must be a superset of what's actually in use, not a replacement for it.

## 4. Fonts

- All web fonts MUST be **self-hosted** as WOFF2 files under `themes/tapestry/static/fonts/<style-name>/<variant-name>/` and committed to the repository. No fonts may be loaded at runtime from an external CDN — Google Fonts (or any other font service) is used only as the upstream source from which files are downloaded and vendored, never as a live delivery mechanism.
- Multiple presentation styles may each pair different typefaces for headings, body, and code. Each presentation style must have a fully specified, tested typeface pairing, with the WOFF2 files committed under the corresponding `<style-name>/<variant-name>/` subdirectory.
- For each presentation style:
  - Heading typeface: <name, weights required, e.g. "Fraunces 600, 900">.
  - Body typeface: <name, weights required, e.g. "Inter 400, 500">.
  - Code typeface (if used): <monospace, weights required, e.g. "Space Mono 400, 700">.
  - Fallback stack for each: metric-adjusted system font fallbacks (see `_fonts.scss`) plus generic family, e.g. `Fraunces, 'Fraunces Fallback', Georgia, serif`.
- Only **latin and latin-ext subsets** are vendored by default. Additional subsets (cyrillic, greek, vietnamese, etc.) may be added per-variant if the site's content requires them, but are not required.
- Variable fonts (covering a continuous weight range in a single file) are preferred over separate per-weight static files where the upstream font supports them.
- All `@font-face` declarations MUST use `font-display: swap`.
- `<link rel="preload">` hints MUST be added in `base.html` for each variant's primary body and heading font (latin subset), using `get_url()` without `cachebust=true` — the preload `href` and the `@font-face src` path must stay byte-identical or the browser will fetch the file twice.
- The font choice must pass WCAG AA readability at the smallest body text size used in the site (typically 14–16px).

## 5. Layout grid system

- All presentation styles MUST be built on a **12-column responsive grid system**. This applies to every shipped template (page, section, index, archive, taxonomy list/single, 404) and every preset style — no style may opt out or substitute a different column count.
- The grid must be implemented in CSS only, per §2 (no JS-driven layout). CSS Grid (`display: grid` with a 12-column `grid-template-columns`, e.g. `repeat(12, 1fr)`, or an equivalent fractional definition) is the reference mechanism.
- Content regions (article body, sidebars, pagination, footer columns, etc.) must span a documented, deliberate number of the 12 columns at each breakpoint — not arbitrary percentage or pixel widths.
- Breakpoints and their per-breakpoint column spans are frozen design tokens (see §8) and must be documented in each style's `specs/design-tokens-<style-name>.md` alongside colour, spacing, and type tokens.
- The grid must remain fully responsive down to a minimum viewport width of 320px without introducing horizontal scrolling of the page itself (per §1 accessibility requirements).
- The overall content container is capped at a frozen **maximum width of 1200px**, shared across every group/variant (verified in `prototypes/spikes/responsive-grid-spike.html`). This is a deliberate departure from terminus's own narrow ~864px `layout-center` column — Tapestry's presentation styles are wide editorial/research-profile layouts (as prototyped in `prototypes/style-tiles/`), not a reproduction of terminus's terminal-width aesthetic. No style or variant may substitute a narrower fixed column width in its place.
- On the single-article template, the columns 9–12 sidebar region is **content-driven, never unconditionally reserved**: it occupies grid space only when it actually has something to render (an automatic "on this page" heading TOC, and/or custom content via `page.extra.sidebar` pointing at a colocated Markdown snippet), and a page may force it off entirely with `page.extra.sidebar = false`. Whenever no sidebar renders, the article body MUST reclaim the full 12 columns — leaving columns 9–12 empty while the article stays at its narrower 1–8 span is a constitutional violation of this section, not an acceptable default state.

## 6. Navigation

- The main site navigation MUST collapse into a disclosure/hamburger pattern below a defined breakpoint. This applies to every preset presentation style and every variant within it — no style or variant may opt out, substitute an always-expanded nav, or otherwise skip the collapse.
- The collapse MUST be implemented without JavaScript, per §2. The native HTML `popover` attribute with a `popovertarget` invoker (as terminus itself uses for its own main menu at the pinned snapshot), the `<details>`/`<summary>` element, or an equivalent CSS-only mechanism (e.g. the checkbox hack) are acceptable reference mechanisms. Terminus's own `close_responsive_menu_on_resize` JS auto-closer is explicitly out of scope here — per §2, it must be reimplemented without JS or dropped, never carried forward to satisfy this requirement.
- The collapse breakpoint, and the collapsed/expanded visual treatment either side of it, are frozen design tokens (see §8) and must be documented per style/variant, consistent with how grid breakpoints are documented under §5.
- The collapsed state MUST remain fully keyboard-operable (open, navigate between items, close) and expose correct ARIA/disclosure semantics, per §1. This is non-negotiable regardless of how few items a given style's sample navigation happens to show — the mechanism must not silently rely on there being few enough items to fit on one line.

## 7. Presentation styles

- The theme ships with a set of **preset presentation style groups** that users can select via theme configuration (e.g. `extra.presentation_style` in `config.toml`).
- Maximum of **5 preset style groups** (e.g. `scholarly`, `creative`, `engineering`, ...). This cap applies to top-level groups only, not to variants within a group (see next bullet) — a group may offer as many variants as prototyping produces.
- Each group may offer multiple **variants**: distinct, fully-specified pairings of typefaces, colour tokens, spacing, and layout decisions that share the group's overall creative intent (e.g. `scholarly` variants: "classic-ivy", "nordic-minimalist", "dark-academia", "scientific-journal", "contemporary-research-lab"). A group with only one viable direction may ship a single variant.
- Variant selection uses a second, group-scoped configuration key, e.g. `extra.presentation_variant` in `config.toml`. Each group MUST designate one variant as its default, used when `extra.presentation_variant` is unset or names a variant that does not exist within the selected group.
- **Theme-wide default, and migration from terminus:** if `extra.presentation_style` is unset, or names a group that does not exist, Tapestry MUST default to the **`scholarly`** group; within `scholarly`, the default variant is **`contemporary-research-lab`**. This default applies unconditionally, including when a site is migrating from terminus with `theme = "tapestry"` newly set but no `presentation_style`/`presentation_variant` supplied yet. Any terminus-only keys still present in that site's config (e.g. `extra.color_scheme`, `extra.color_scheme_switcher` — see §2's theme-switcher scope note and `specs/terminus-compat-contract.md` §9) are inert in Tapestry and MUST NOT be read, mapped, or migrated into an equivalent presentation style/variant. Tapestry's default applies exactly as if those leftover keys were absent — there is no automatic scheme-to-style translation.
- The number of groups, their names, the number of variants per group, variant names, and their specific typeface pairings are to be determined during prototyping and documented separately (not in this constitution).
- All preset style groups — and every variant within them — must independently satisfy the requirements in §1 (WCAG AA), §4 (fonts and readability), §5 (12-column grid), and §6 (navigation collapse).

## 8. Design tokens

- Each presentation style group has a frozen set of design tokens documented in `specs/design-tokens-<group-name>.md` (e.g. `design-tokens-scholarly.md`), containing one section per variant. Tokens are discovered and approved during prototyping; once approved, they become the spec for CSS/template implementation.
- **Every variant of every presentation style group must provide both light and dark mode variants.** Users can select any group/variant combination regardless of their `prefers-color-scheme` preference.
- Design tokens for each variant must include:
  - Colour palette (light mode and dark mode): named CSS custom properties with hex values for each mode, e.g. `--colour-bg-primary: #ffffff` (light), `--colour-bg-primary: #1a1a1a` (dark). These values are toggled by the theme switcher.
  - Spacing scale: base unit and multiples (e.g. `--space-xs: 0.5rem`, `--space-sm: 1rem`, `--space-md: 1.5rem`...).
  - Type scale: `--font-size-h1`, `--font-size-body`, `--font-size-small` with rem or px values, and corresponding `--line-height-*` values.
  - Border radius (if applicable): `--radius-sm`, `--radius-md`.
  - Shadows (if applicable): `--shadow-sm`, `--shadow-md` for layering.
  - Decorative background pattern (optional, per variant): `--pattern-bg-image` / `--pattern-bg-size` (light and dark mode values). Not every variant needs one — a variant that doesn't use one simply resolves both tokens to `none` / `auto`. This must stay CSS-only, per §2 — a `background-image` gradient/pattern declaration, never a raster or vector asset — rendered behind body text. It is subject to a documented contrast ceiling: a full-bleed line/dot-grid pattern must use a low enough alpha (in practice ≤0.15) that it does not measurably erode the ≥4.5:1 AA contrast already verified for `--colour-text-primary` against the flat `--colour-bg-primary` (§1); a sparse point decoration (e.g. a handful of star-like dots per pattern tile) is exempt from that alpha ceiling itself but must still leave enough of the tile's flat background exposed that the same aggregate contrast holds. Verified the same informal way the flat colour pairs below are, during prototyping.
  - Grid breakpoints and column spans (see §5): named custom properties or documented values for how each region maps onto the 12-column grid at each breakpoint.
  - Navigation collapse breakpoint and treatment (see §6): the viewport width at which the nav collapses, and the documented expanded/collapsed styling either side of it.
- All colour values must be verified to maintain WCAG AA contrast ratios in both light and dark mode, for every variant, before the token set is approved.
- **Alert colours are shared and mode-scoped, not per-variant.** GitHub-style alert/callout semantics (`note`, `tip`, `info`/`important`, `warning`, `danger`/`caution`) use one `--alert-<type>-border` / `-bg` / `-code` token set per mode (light/dark), defined once in `themes/tapestry/sass/css/_variants.scss` and shared unmodified by every group and variant — they are deliberately excluded from the per-variant token list above and from `specs/design-tokens-<group-name>.md`. Reason: the semantic hue (danger=red, tip=green, info=blue, warning=amber, note=grey) is meaningful independent of a site's chosen aesthetic, so it must not shift between e.g. `scholarly` and `creative`. Because the tokens are shared, they must clear §1's ≥4.5:1 AA floor against the *composited* alert background (`color-mix(in srgb, --alert-<type>-bg 12%, transparent)` over whichever `--colour-bg-primary`/`-bg-secondary` the alert actually renders on) for every group/variant's light and dark mode simultaneously, not just the group being actively worked on — a value tuned to clear one group's backgrounds can still fail a warmer/darker-background group. These tokens exist in three places that must be kept byte-identical for a given mode: the light defaults in `:root`, the dark defaults in `@media (prefers-color-scheme: dark) { :root { ... } }`, and the theme switcher's explicit `html[data-color-mode='light']` / `html[data-color-mode='dark']` overrides — a fix applied to only one of the light-mode copies silently leaves the other in place.

## 9. Brand identity

- The theme MUST use the approved Tapestry logo, rendered via `currentColor` so it inherits each preset style's own colour tokens rather than carrying a fixed colour. The full specification, usage rules, and canonical source files are frozen in `specs/brand-logo.md`.
- The logo's wordmark portion MUST be vector outlines, not live text, so it renders identically regardless of whether any web font is installed or downloads successfully. Brand identity may not silently depend on network font availability.
- The logo is a single frozen asset shared across every preset style group and variant — unlike fonts, colours, and tokens (§8), it does not get redrawn or recoloured per style. Any request to reskin the logo per style is a constitutional conflict; flag it rather than silently complying.

## 10. Amendments

- Any new non-negotiable belongs here, not in CLAUDE.md.
- State new clauses as direct, verifiable requirements ("contrast ratio ≥ 4.5:1 for body text"), not vague guidance ("follow best practices").
- When adding or changing a clause, record the date and reason as a new entry in [CONSTITUTION-CHANGELOG.md](CONSTITUTION-CHANGELOG.md), so drift over time stays visible. That file is history only; this file is the complete statement of the current rules and must not be left relying on it.
